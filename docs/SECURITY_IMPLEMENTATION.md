## 会话生命周期与资源上限（第二批）

消息删除的后续实施状态见 [MESSAGE_DELETION.md](MESSAGE_DELETION.md)：服务端权限/事务/事件分页、客户端持久删除标记、删除按钮及确认/结果流程已接入，尚未运行验证。部署前新增手动迁移 004_message_deletion.sql，不应忽略其对历史查询的依赖。

- 每条聊天 TCP 连接使用独立 Asio strand，读写、定时器和实际关闭操作在该串行执行器中处理；关闭标记使用原子变量，重复关闭无副作用。
- 接入后 15 秒内必须完成登录；收到头部后 15 秒内必须完成包体。等待下一个完整包头的上限为 120 秒，分片输入不会反复延长同一阶段的截止时间。
- 120 秒指网络接收空闲，不是用户离开电脑后的自动登出。现有客户端后台同步请求会维持连接；休眠或长期断网后需要重新连接。
- 单连接采用令牌桶，每秒恢复 40 个包额度，最多突发 80 个；耗尽即断开。每个聊天节点最多保留 4096 个连接。这些是初始保护值，未经容量验证，不是吞吐承诺。
- 跨线程待派发发送任务与实际发送队列分别受 MAX_SENDQUE 限制，超限断开；正在异步发送的缓冲区保留至取消完成，避免提前释放。
- 同一节点上替换账号连接时关闭旧连接，关闭操作放在用户映射锁外。跨节点仍依赖 Token 复查，不是完整多设备体系。
- 关闭后队列中的普通业务请求丢弃；已经完整收到的注销请求仍检查并撤销匹配 Token，避免客户端发送注销后紧接 EOF 导致撤销被丢弃。
- 仅完成编译检查，未运行超时、并发、限流或压力测试。尚无可信代理来源 IP 解析，因此没有把回环代理 IP 冒充为最终用户 IP 做设备识别。

没有运行应用、联网联调、测试、数据库迁移或邮件发送。仅构建检查不能验证安全属性。

## 现在如何使用本机开发模式

客户端注册和重置密码已取消旧的 6～15 位 ASCII 限制：C++ 控制器和服务端统一要求 8～128 个 UTF-8 字节且不含 NUL；支持中文等字符，但中文通常占 3 个字节。验证码输入为六位数字。登录错误读取服务端的 `message` 字段，以便展示旧账号重置密码提示。

资源回收补充：邮箱查无结果也会归还 MySQL 连接；更新密码以实际受影响行数判断成功；连接初始化、重连和健康检查结果集用作用域对象管理。连接池等待有上限，但底层数据库调用仍需进一步配置网络超时，不能据此宣称所有操作都有超时保障。

1. 所有进程在同一台受信任 Windows 机器运行。未设置 SAKURA_SECURITY_MODE 时为 development；这不是生产安全模式。
2. GateServer HTTP 与 ChatServer TCP 只绑定 127.0.0.1。开发模式的内部 RPC 也只绑定回环，客户端不允许连接远程明文地址。
3. 客户端 config.ini 没有 Security/Mode 时使用 development，原本机 HTTP/TCP 端口不变。
4. 手动选择正确的 skrchat 数据库，备份后执行 database/003_privacy.sql。缺少隐私表时相关操作按失败处理，不绕过隐私限制。本次未执行脚本。
5. user.pwd 必须能够容纳完整 Argon2id 字符串（现有 schema.sql 是 VARCHAR(255)）。新注册/改密使用 libsodium Argon2id（interactive 参数）。不提供明文密码登录回退；旧账号通过邮箱重置密码升级，用户和聊天数据不删除。
6. 验证码由六位安全随机数字组成，3 分钟有效，同用途邮箱 60 秒发送间隔，每个验证码最多 5 次校验。注册与重置 key 分开；成功验证后原子消费，后续业务失败也需要重新获取。验证码临时保存在 Redis，不输出到日志。
7. 新的登录会替换该账号旧 Token，当前仍是单活动会话模型，不是完整多设备管理。退出通过 1042 尝试撤销；网络故障下不能保证注销请求送达，服务端到期或再次登录会替换旧会话。
8. 客户端侧边栏齿轮打开隐私设置。1040/1041 为设置协议；0=所有人，1=好友，2=仅自己/拒绝申请。资料范围控制昵称、头像、简介和性别，不隐藏作为身份标识的用户名、UID。

## 生产模式（证书缺失时不回退）

尚未配置/启动生产环境；没有自动生成、安装或信任证书。域名不是本机试配的必要条件，但证书 SAN 必须匹配实际连接的 DNS 名或 IP。不要使用 ignoreSslErrors 或跳过验证。

各个 C++ 服务进程设置以下环境变量（CLion Run Configuration 的 Environment variables）：

```
SAKURA_SECURITY_MODE=production
SAKURA_RPC_CA=<受信任 CA PEM 文件路径>
SAKURA_RPC_CERT=<该服务自己的证书链 PEM 路径>
SAKURA_RPC_KEY=<该服务自己的私钥 PEM 路径>
```

证书：网关 SAN 包含 sakura-gate；聊天节点 SAN 包含 sakura-chat。服务器证书还需包含其被连接的实际 DNS 名/IP。不要让不可信服务拥有签发其他角色证书的权限。StatusServer 只允许 sakura-gate 签发 Token；聊天通知只允许 sakura-chat。

Node 验证服务同样配置上述变量。由于当前 grpc-js API 不暴露足够的服务证书身份信息，验证服务额外检查 SAKURA_VERIFY_SERVICE_KEY；此随机服务密钥至少 32 字符，仅网关与验证码进程持有，且只在 mTLS 内传输。不要提交到仓库。

HTTP 和聊天公网连接由同机 TLS 代理终止，模板见 deploy/nginx-security.conf.example。代理到程序的明文流量只能留在本机回环；跨机器时每个节点分别部署代理，不把 8090/8091 暴露到其他机器。

StatusServer 的 ChatServers 节点配置要返回 TLS 代理地址与端口（示例 18090/18091），不是内部裸 TCP 端口；RPC 配置端口仍保持对应内部 RPC 端口。客户端示例：

```ini
[Security]
Mode=production
CaFile=C:/sakura-certs/ca.pem
[GateServer]
host=localhost
port=8443
url=https://localhost:8443
```

CaFile 是应用专用信任配置，不自动修改系统证书库。公众部署须改成自己的地址和可信证书。缺失证书会导致生产 RPC 启动/连接失败，而不是使用不安全连接。模板未启动或验证。

## 部署前必须完成

本轮新增环境凭据注入与生产缺失检查，配置方法见 [SECRET_CONFIGURATION.md](SECRET_CONFIGURATION.md)。默认开发模式保持兼容；不会自动设置 IDE/系统环境变量或轮换现有凭据。

- 轮换曾进入 Git 或日志的真实密码/邮件凭据；删除文件不等于撤销泄露。现有历史日志和配置未自动清理，避免误删。
- 生产数据库/Redis 只允许内部访问，使用专用最小权限账号；已支持环境凭据注入，但现有配置文件、凭据轮换、跨机传输保护与集中秘密管理仍待完整迁移。
- 密码哈希使用 SODIUM_ROOT 指向本机 libsodium 静态库；当前可发现安装位于 D:/environment/Anaconda3/Library，换机器需自行配置，不是仓库内置依赖。
- TLS 代理之后当前网关按直接连接 IP 限流，会聚合代理后的用户；必须结合代理侧限流/受信任转发地址机制后再上线。
- 黑名单阻止新申请和新消息，不删除旧记录。并发中的已接受消息可能仍到达。资料/已读隐私不能收回别人已见到、截取或缓存的数据。
- 关闭已读开关只停止新已读记录，不删除旧回执；本地的已读标记用于自己清除未读数，不等于向对方发送回执。
- 旧 Redis 用户资料缓存可能含历史敏感字段；新代码不再写入/读取密码，但旧缓存未自动删除。
- 需要另行授权并执行畸形包、越权、过期/撤销、跨节点、验证码重放、证书失败与数据库错误场景验证。
