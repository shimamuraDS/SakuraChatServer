# 消息删除与删除事件同步

## 当前状态

已实现服务端删除接口、账号级持久删除事件、客户端轮询和本地删除标记，并接入消息下方删除按钮、二次确认、单请求等待及结果提示。未运行界面、接口、并发或离线恢复测试。

客户端仅为有服务器 message_id 的消息显示删除入口；发送中或未确认落库的消息暂不支持删除。默认仅为自己删除，只有自己发送的消息显示“同时为对方删除”勾选项。后端仍独立检查权限，不信任界面限制。

等待确认期间禁止重复提交；8 秒无回包或连接中断提示结果未知，不承诺操作未生效。确认成功后先在本地事务保存删除标记并移除消息/回执，再刷新列表；不使用删除回包推进事件游标，防止跳过其他删除。若本地处理失败，提示服务器已确认但缓存需恢复，并继续依靠事件同步。应用锁锁定时关闭确认弹窗，禁止发起新请求，不撤销锁定前已授权发出的请求。

运行新服务前，备份并手动执行 `database/004_message_deletion.sql`，前提是已有聊天持久化表。脚本仅建表，不主动删除业务记录；本轮未执行 SQL。新版历史查询依赖新表，缺表会失败，不应直接用未迁移数据库启动验收。

## 权限与语义

- 1044 请求 / 1045 响应：字段 `request_id` 为 UUID，`message_id` 为十进制字符串，`for_everyone` 为布尔值。
- 操作人只取已认证连接 UID，不接受客户端指定 actor。
- 参与者可以对自己删除；对方的副本保持原样。发送者才能对双方删除，接收者不能替发送者删除双方副本。本实现不照搬 Telegram 的全部删除权限。
- 双方删除在同一事务里清空服务器当前记录的 content/extra、标记 status=2，并给双方写入删除事件。保留消息主键、序号、参与者及删除标记用于幂等和同步，不是删除全部元数据。
- 重复删除不会重复产生事件；删除后原发送 UUID 的重试返回删除状态，不再插入消息。
- 单方删除不清空对方仍需访问的云端正文，历史回包对该账号只返回空正文及 message_status=3，以保留历史序号推进。

## 离线与跨端同步

1046 请求 / 1047 响应：传 `request_id` 和字符串 `after_event`；返回 `items`、`next_event`、`has_more`，每项包含 `event_seq`、`message_id`、`sender_uid`、`msgid`。

事件只查询当前账号。序号分配在账号计数行锁保护下完成，多账号按 UID 升序加锁；锁保留至提交，避免直接使用自增 ID 时出现“较大 ID 先提交，游标越过稍后提交的小 ID”。分页同时限制条数与包字节数。

客户端约每 10 秒轮询，分页未结束时继续拉取。删除消息缓存、清理待发回执、保存 local_deleted 标记及推进删除游标，在同一个本地事务内提交。消息发送重试、迟到推送和历史合并都检查删除标记，避免重新写入。该同步可以用于同账号以后登录的客户端，不代表已经支持多设备同时在线。

## 限制与后续工作

- 没有实时删除推送：在线端可能等待下一次轮询；离线端必须重新联网才能获知。网络错误时不可能保证立即清除其他机器副本。
- 删除事件不自动清理，否则长期离线客户端可能漏掉删除；后续需设计事件保留期、全量校验和备份恢复策略。
- 初次同步、旧客户端、已送达截图/导出、缓存备份、MySQL binlog/备份及磁盘残留不可能靠该接口远程擦除；不能宣称安全擦除。
- 单方删除还未在所有旧协议回包路径统一隐藏元数据；新版客户端依靠持久标记抑制迟到内容。不要用旧版客户端承诺一致的删除体验。
- 新发私聊消息已增加自动删除期限，见 [AUTO_DELETE.md](AUTO_DELETE.md)；尚无撤销删除及群聊删除。失败或结果未知时可再次确认删除，由服务端按消息主键幂等处理；未提供离线删除命令队列。
- 需要后续授权运行并验证越权、重复提交、并发事件提交顺序、分页中断、重登录、迟到推送及本地提交失败场景。编译成功不验证这些安全属性。
